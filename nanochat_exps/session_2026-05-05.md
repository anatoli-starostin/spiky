### Theoretical takeaway

exp144's qk_lut emits 32 Borda values that V2D constructively maps onto the manifold (every move in Borda space → structured move in dominance space, no information loss). exp152/153 has qk_lut emit 496 *unconstrained* dominance scores that get *averaged* via Borda's 1/√31 projection — many vote configurations collapse to the same Borda vector. The optimizer can't sharpen Borda values past a noise floor because each vote's contribution is small relative to others' randomness. **BitPermutationLUT** addresses this by baking pair anti-symmetry into the scatter (each table contributes `+v` to slot a and `-v` to slot b for canonical pair (a,b)) — pair selection is still random per table but the anti-symmetric vote structure makes each output channel a *meaningful* (a,b) pair from the start.

## BitAttention backward optimization

### Initial state

`_BitAttentionFn.backward` re-ran F.scaled_dot_product_attention with autograd to obtain dq/dk/dv. Wasteful (recomputes the forward fully) and obscures the structure.

### Step 1: explicit closed-form backward (PyTorch reference)

Replaced autograd-through-SDPA with explicit `dV = A^T @ dO`, `dA = dO @ V^T`, `dS = A * (dA - rowsum(A·dA))`, `dQ = dS @ K * scale`, `dK = dS^T @ Q * scale`. Eliminates redundant forward pass; structures the code around the matmul boundary where the bit-trick lives. **102/102 tests pass at atol=1e-5 vs F.SDPA autograd**.

### Step 2: custom CUDA WMMA kernel with bit-packed K

Wrote four kernels in `lutorch.cu`:

| Kernel | Approach | Speed at d=2016 BH=8 |
|--------|----------|----------------------|
| `bit_attn_signed_accum_kernel` | naive global-mem float·{−1,+1} | 2.45 ms |
| `bit_attn_signed_accum_tiled_kernel` | register-tiled, 8 d/thread | 1.68 ms |
| `bit_attn_signed_accum_wmma_kernel` | fp16 WMMA + bit decomp | 1.05 ms |
| `bit_attn_signed_accum_wmma_int8_kernel` | int8 WMMA, per-tile dynamic scale | 1.49 ms |
| cuBLAS sgemm (PyTorch reference) | — | 0.67 ms |

**Honest finding**: hand-rolled WMMA didn't beat cuBLAS sgemm on H100. cuBLAS dispatches to TF32 Tensor Cores at ~6 TFLOPs sustained (10× more TC-efficient than my WMMA at ~12 TFLOPs of fp16 TC peak ~989). To match cuBLAS-tuning level requires CUTLASS-style techniques: cp.async, double-buffered shared mem, software-pipelined wmma loads. Tried double-buffering (occupancy dropped, slower); int8 with per-tile dynamic scale (max-reduction overhead negated the TC throughput gain).

### Step 3: bf16 cuBLAS path = WGMMA on Hopper

Realized that **cuBLAS bf16 GEMM dispatches to WGMMA on Hopper** (sm_90's `wgmma.mma_async.sync.aligned.m64n256k16` instruction). Q, K are ±1 → bf16 cast is *lossless*. Just casting inputs to bf16 and using `torch.matmul` unlocks WGMMA throughput.

```python
# Precision-exploiting bf16 fast path (env: SPIKY_BIT_ATTN_USE_BACKWARD_KERNEL=bf16)
q_bf, k_bf = q.to(torch.bfloat16), k.to(torch.bfloat16)
s = torch.matmul(q_bf, k_bf.transpose(-2,-1)).to(torch.float32) * scale  # WGMMA
# ... softmax, dV (fp32), dA (fp32), dS eltwise ...
ds_bf = ds.to(torch.bfloat16)
dq = torch.matmul(ds_bf, k_bf).to(torch.float32) * scale     # WGMMA
dk = torch.matmul(ds_bf.transpose(-2,-1), q_bf).to(torch.float32) * scale  # WGMMA
```

dV and dA stay fp32 (their inputs A, grad_o are real-valued floats with wider dynamic range; bf16 cast risks precision loss). dS picks up bf16 quantization on dQ/dK only (~1e-3 relative). 110/110 tests pass (8 new bf16-path correctness tests added with relaxed atol).

### Final benchmarks (H100, BH=8, T=512)

| d | fp32 cuBLAS | bf16 (WGMMA) | F.SDPA fp32 fwd+bwd | F.SDPA bf16 fwd+bwd | bf16 vs fp32 cuBLAS |
|---|---|---|---|---|---|
| 496  | 0.260 ms | 0.238 ms | 0.434 ms | 0.585 ms | 1.09× |
| 992  | 0.396 ms | 0.237 ms | — | — | 1.67× |
| 2016 | 0.681 ms | **0.310 ms** | 0.754 ms | 0.931 ms | **2.19×** |
| 4096 | 1.256 ms | **0.516 ms** | 1.373 ms | 1.677 ms | **2.44×** |
| 24 × 2016 | 2.054 ms | **0.852 ms** | 2.187 ms | 2.627 ms | **2.41×** |

**Our bf16 path is 2.4× faster than F.SDPA fp32 fwd+bwd combined** (and we only count backward), and 3.0× faster than F.SDPA bf16 fwd+bwd. cuDNN's flash backward at bf16 is *slower* than at fp32 (cuDNN doesn't seem to have an optimized bf16 backward path for our shape).

### What didn't work

- **My hand-rolled WMMA kernel**: 1.5× *slower* than cuBLAS sgemm. The CUTLASS-tuning gap is the issue, not the bit-trick. To match cuBLAS would need cp.async + warp-specialized loaders + double-buffer (multi-day work) — and even then the bit-trick advantage doesn't materialize on H100 because the problem is compute-bound, not memory-bound (we're at 2% of peak memory bandwidth).
- **int8 WMMA with per-tile dynamic scale**: the max-reduction + 2-pass quantize overhead negated the int8 TC throughput gain. Slower than fp16 WMMA.
- **FP8 via `torch._scaled_mm`**: not natively batched, so a Python loop over BH adds heavy overhead. Even ignoring overhead, precision was ~2.6% rel-median (vs bf16's ~1e-3) — global scale not adequate.
- **Double-buffered WMMA**: occupancy dropped from 32 warps/SM to ~16, and without cp.async the load/compute don't actually overlap → slower than single-buffered.

### What would beat our current bf16 path (deferred)

- **Flash-style backward** that doesn't materialize T² intermediates (S, A, dA, dS). Saves ~32 MB of memory traffic at d=2016 BH=8. cuDNN does this for fp32 but not as well for bf16. A hand-rolled flash backward exploiting ±1 Q/K could be 1.5-2× faster than our explicit path. Multi-day CUDA work.
- **Native batched FP8 GEMM with per-row scaling**: H100 fp8 TC peak is 4× bf16. With proper kernel, could reach 0.15 ms at d=2016 BH=8. Significant infrastructure work (cublasLt fp8 path).

## Continued: CUTLASS-tuned bit-packed forward kernel

After landing the bf16 backward, the forward bit-packed flash kernel (no Tensor Cores) was the next bottleneck — 3-4× slower than cuDNN flash forward. Built a real CUTLASS-tuned kernel exploiting BOTH halves of attention as Tensor Core ops:

### `bit_attn_flash_fwd_tc_kernel` final design

| Step | Operator | Tensor Core path |
|---|---|---|
| Q @ K^T (popcount) | `bmma.sync.aligned.m8n8k128.row.col.s32.b1.b1.s32.xor.popc` | **Hopper binary TC** (49,152 TOPS peak) |
| A @ V | `mma.sync m8n32k16` bf16 → fp32 | bf16 TC (989 TFLOPs peak) |
| Online softmax + correction | fp32 in shared mem | (no TC needed, small) |

**Layout**: 4 warps/block × 8 q_rows = 32 q_rows per block; K_TILE=16 (matches WMMA bf16 K=16); V cast to bf16 per K-tile (cooperative across all 128 threads); A cast to bf16 per warp after online softmax. O accumulator round-trips through O_acc shared mem (load → mma_sync → store) so per-q-row corrections apply cleanly.

### Forward bench at H100 sm_90, BH=8, T=512

|---|---|---|---|---|

Precision: ~2e-3 relative median (bf16 quantization on A and V; same profile as the bf16 backward path).

### Architectural note on matmul-free claim

The TC forward kernel preserves **bit-storage native** processing: Q and K are bit-packed throughout; the bmma operates directly on bits. The bf16 cast happens only on A (softmax probs, derived) and V (intermediate values), not on Q/K. The matmul-free claim for the LUT outputs of forward is intact.
