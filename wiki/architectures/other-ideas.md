# Other ideas

Architectures that were tried once and do not belong to a line of the [main sections](README.md). Each entry says what the code does and what was recorded; none of them has a conclusion, and none is part of a result quoted elsewhere in the wiki.

## [`pcalm_lut`](https://github.com/anatoli-starostin/spiky/tree/672344d6d379b6a889c42174430d4216252cbf05/research/pcalm_lut): predictive coding with LUT layers (September 2026)

This study was done almost entirely by an AI agent, with almost no human intervention: all 53 commits of the folder are by the bot account of the Claude agent, between 2026-09-21 and 2026-09-23, and the human part was the brief and the occasional redirection. Read it as an agent's exploration whose conclusions have not been reviewed.

**The problem.** In a LUT layer the address is an integer chosen by hard sign comparisons, so no gradient flows through it. The gradient reaches the layer's input only through a surrogate: in the confidence-weighted layer, through the confidence score (see [Gradient backpropagation](../lookup-table-primitives/backpropagation.md#4-gradient-through-the-confidence-score)). Ordinary backpropagation composes this surrogate across all the layers of a deep stack, and it is not known how much error that accumulates with depth. The question of the study: can a deep stack of LUT layers be trained with methods that use the surrogate only locally, once per layer, and never compose it across layers?

**The setup.** The model is a residual stack of [`LightMultiHeadLUT`](https://github.com/anatoli-starostin/spiky/blob/c4a750b2f9ab65efe6a61254103a92d6fd8fc2a2/src/spiky/lutorch/light_multi_head_lut.py) blocks (the confidence-weighted layer with the `margin` score, two table rows read per lookup, constant cells; see [FFN replacement](transformers/ffn-replacement.md#4-fixed-evaluation-confidence-forms-and-parity-that-does-not-last-september-2026)). Block $i$ computes $h_i = h_{i-1} + a_i \mathrm{LUT}_i(h_{i-1})$ and there is a linear map in from the flattened image (28 by 28 pixels, MNIST or Fashion-MNIST) and a linear readout to the ten classes. The main configuration has width 32 and 16 tables of 8 anchor pairs per layer; depths from 4 up to 64 were used, with scale factors chosen as in the external paper. All trainers share the same model, initial weights and data order, and take one optimiser step per batch, so their curves are comparable per step; the wall clock is not, because predictive coding pays several inner iterations per step, and the study reports both. The code works with `LightMultiHeadLUT` in a residual stack and compares three trainers ([pcalm.py](https://github.com/anatoli-starostin/spiky/blob/672344d6d379b6a889c42174430d4216252cbf05/research/pcalm_lut/pcalm.py)):

- ordinary backpropagation;
- *predictive coding* (PC): the hidden states of the layers are free variables, and each layer is asked to predict the next one, so that $h_i \approx f_i(h_{i-1})$ holds, and the states relaxed by a few inner iterations before one weight step (the surrogate gradient of a LUT layer is then used once per layer per iteration, and is never composed across layers);
- *augmented-Lagrangian predictive coding* (PC-ALM): the same with the constraints $h_i = f_i(h_{i-1})$ enforced by multipliers and a quadratic penalty, following the algorithm of an external paper (Seely and Gould, arXiv 2605.31022, as cited in the code).

Later parts of the folder ask different questions. A variant with a paired backward stack is trained by difference target propagation. An autoencoder asks whether a LUT stack can carry information through a narrow bottleneck (Fashion-MNIST, 784 to 64 and back, mean squared error of the reconstruction; the question is whether LUT layers can use the combinatorial capacity of a low-dimensional vector), first with `LightMultiHeadLUT` blocks and then with [`CompressionMHL`](https://github.com/anatoli-starostin/spiky/blob/3ac72cca40c63b77d509d4ccff33bb85d43e515e/src/spiky/lutorch/compression_mhl.py#L59-L258). A small vision transformer with LUT parts is trained as an autoencoder on Fashion-MNIST at 28 by 28, with probes of the table utilisation and of the attention. The derivations are in [DERIVATION_v2.md](https://github.com/anatoli-starostin/spiky/blob/672344d6d379b6a889c42174430d4216252cbf05/research/pcalm_lut/DERIVATION_v2.md). The conclusions are only in the commit messages and we did not read the runs in depth; examples are "pure difference target propagation, and the first matched-optimiser win over BP", "2000-step autoencoder runs -- the linear baseline still wins", and "CompressionMHL autoencoder, L=2 at width 128 -- four arms, none beat the linear floor" ([commit list](https://github.com/anatoli-starostin/spiky/commits/672344d6d379b6a889c42174430d4216252cbf05/research/pcalm_lut)). It is a credit-assignment study rather than an architecture, kept here because it has nowhere else to go. This direction has to be explored properly, with human-designed experiments; it is not considered a dead end. Folder: [research/pcalm_lut](https://github.com/anatoli-starostin/spiky/tree/672344d6d379b6a889c42174430d4216252cbf05/research/pcalm_lut).

## The byte-level [`RecursiveMultiHeadLut`](https://github.com/anatoli-starostin/spiky/blob/e85a5ceca156e79d199b0f6b395aa8e7e4ee287a/transformer_exps/exp050_mini_recursive_ffn/train.py#L33-L72) (April 2026)

A module that applies a LUT repeatedly: it makes $n$ passes. Each of the first $n-1$ passes adds a refinement of the input back to it,

$$x \leftarrow x + \mathrm{LUT}(x)$$

and the last pass is the ordinary output. When the table already maps the width to itself, its own tables are reused (no extra parameters, twice the compute); otherwise a separate square table does the refinement. Two byte-level runs used it for the output projection and the feed-forward of a small model with width 32 (vocabulary 257, context 32, 50k steps, validation cross-entropy, old evaluation):

- [`exp050`](https://github.com/anatoli-starostin/spiky/tree/e85a5ceca156e79d199b0f6b395aa8e7e4ee287a/transformer_exps/exp050_mini_recursive_ffn), with weights shared across passes: stopped at step 18,000 at 2.12, with no later result;
- [`exp051`](https://github.com/anatoli-starostin/spiky/tree/e85a5ceca156e79d199b0f6b395aa8e7e4ee287a/transformer_exps/exp051_mini_recursive_no_sharing), with separate refinement tables for every LUT (8.9M parameters): finished at 1.8827 (best 1.8813).

The sizes differ from the earlier runs of the series (for example 1.9421 at 5.0M and 1.7685 at 10.0M parameters without recursion), no conclusion was written, and the code was not used again ([exp050](https://github.com/anatoli-starostin/spiky/tree/e85a5ceca156e79d199b0f6b395aa8e7e4ee287a/transformer_exps/exp050_mini_recursive_ffn), [exp051](https://github.com/anatoli-starostin/spiky/tree/e85a5ceca156e79d199b0f6b395aa8e7e4ee287a/transformer_exps/exp051_mini_recursive_no_sharing), [SUMMARY](https://github.com/anatoli-starostin/spiky/blob/e85a5ceca156e79d199b0f6b395aa8e7e4ee287a/transformer_exps/SUMMARY.md#phase-3-mini-architecture-exp048073)).

## Recursive setups in general

Models that apply the same block several times (weight-shared depth, tiny recursive reasoning models) are an open area that has not been started for LUT models. The repository has literature notes on two such models and runs of the original (non-LUT) tiny recursive model on a puzzle benchmark, but no LUT model of them ([hrm.md](https://github.com/anatoli-starostin/spiky/blob/2175d6904f1fd41f17b1ee8049ad685fa26a43ea/doc/research/hrm.md), [trm.md](https://github.com/anatoli-starostin/spiky/blob/2175d6904f1fd41f17b1ee8049ad685fa26a43ea/doc/research/trm.md)). The byte-level module above is the only recursive LUT that was run.
